# Работа над Daychi

## Первый рабочий день

Прочитайте README.md, AGENTS.md, SECURITY.md, docs/PRODUCT.md, docs/DESIGN.md
и docs/TESTFLIGHT_CHANGELOG.md. Для Expo действуют дополнительные инструкции
apps/practice-app/AGENTS.md: перед изменениями сверяйтесь с документацией SDK 57.
[Навигатор](docs/README.md) отделяет текущие решения от истории и кандидатов.

Доступ к приватному репозиторию выдаёт владелец по GitHub username.
Репозиторий не даёт доступ к production, Apple, Telegram или закрытому корпусу:
для конкретной задачи запросите минимально необходимый доступ отдельно.
В issue/PR используйте синтетические данные.

## Ветки и изменения

```sh
git fetch origin
git switch -c codex/my-task origin/main
```

Перед этим проверьте `git status`. При чужих незавершённых изменениях используйте
отдельный clone/worktree; не делайте reset/clean/stash чужой работы.
Одна ветка — одна задача, PR описывает проблему, итоговое поведение и проверки.
Общий worktree не является источником чистого release snapshot.
Исходники последнего mobile выпуска сверяются по тегам и manifests, а не
по предположению, что HEAD совпадает с бинарником.

Сохраняйте bundle ID, URL-схему, ключи хранения и API-контракты.
Расписание всегда Asia/Jerusalem, даже когда устройство в другом часовом поясе.
Не смешивайте демо в `/prototype` с рабочим продуктом.
Изменение зависимости/номера сборки не должно быть побочным эффектом правки.

## Проверки перед PR

Из корня: `.venv/bin/python -m pytest -q` и
`python3 scripts/check_repository.py --staged` после staging.
В приложении: `npm run typecheck`, `npm run lint`, `npm test`.
Для веб-вики: `npm test`, `npm run build` в apps/wiki-graph;
если bundle изменился, включите соответствующий diff в PR.
Запишите команды, результаты и непройденные проверки.

UI принимается только после парной сверки каждого затронутого состояния с
утверждённым источником из docs/DESIGN.md. Проверяйте реальные пути входа,
back/close, Android Back, смену вкладки, прокрутку, фильтры, выбор и черновики.
Особый список состояний «Моих занятий» находится в AGENTS.md.
CI и Simulator не подтверждают real-device QA.

## Контент и приватные файлы

Не добавляйте каталоги, транскрипты, аудио/видео, приглашения, базы пользователей,
Zoom-реквизиты, `.env`, ключи, профили, IPA/APK или raw-логи.
Даже приватный GitHub не является хранилищем production-данных.
Скриншоты с реальным содержимым вики и списками тестировщиков остаются локальными;
правила и список исключений — в docs/daychi-rename.md.
Автоматическая проверка дополняет ручную проверку и не распознаёт текст в картинках.

Контентные партии выполняются по docs/wiki-contributor-pipeline.md;
источники и результаты вне Git, импорт — у координатора.
После партии обновляется docs/wiki-work-plan.md с выполненным/оставшимся объёмом
и фактическими затратами, когда они доступны.

## Выпуск и решения

PR не запускает deploy или выпуск. Нужны отдельное разрешение владельца,
актуальная QA и неизменный source snapshot. Следуйте AGENTS.md и changelog;
исторические факты не редактируются задним числом.
У продуктовых решений записывайте дату, основание и пределы в соответствующий doc.
Новый кандидат дизайна не становится утверждённым автоматически.
