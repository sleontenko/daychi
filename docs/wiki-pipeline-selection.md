# Выбор пайплайна: проверка по эталону

28 сентября 2026. Владелец подтвердил: свежая Telegram-авторизация находится
на MacBook; обновление базы выполняется отдельной задачей там. Текущая задача —
сравнение ASR с проверенной расшифровкой, не с сервисом «Talon».

## Предлагаемая общая схема

Снимок Telegram → реестр уникальных ресурсов → локальное аудио с хешем →
очередь ASR → исходный транскрипт с таймкодами → проверенная редакция →
черновики статей и словаря со ссылками на фрагменты → проверка → одобрение.

Сохранять исходный ASR отдельно от редакции. Словарь помогает проверять термины,
но не должен незаметно подменять услышанное. Для очереди нужны контроль тишины,
повторяемость, восстановление после остановки и отдельные статусы ошибок.
Конкретный движок и резервный маршрут пока не выбраны.

## Первоначальный вариант с ручной проверкой — заменён

Владелец отклонил ручную подготовку эталона. Раздел ниже сохранён как описание
старого инструмента, а не как требование к владельцу. Актуальная схема — в конце.

### Прежняя методика

1. Первый контроль: пять уже подготовленных фрагментов по 90 секунд. Человек
   расшифровывает их, сначала не читая выводы моделей. Сохраняет произнесённые
   слова, повторы, отрицания и числа; не превращает речь в отредактированную статью.
2. Неразборчивые места отметить отдельно. До их разрешения не выставлять всему
   фрагменту `verified_by_listener=true`: текущая оценка не поддерживает маски
   неопределённых интервалов. Термины проверять по аудио и контексту; сомнения
   фиксировать, а не заменять догадкой.
3. Заполнить `listening-reference.json`: `text`, `reviewer`,
   `verified_by_listener`, заметки по терминологии. Сохранить ID и хеш аудио.
4. Посчитать WER всех трёх моделей на одних и тех же проверенных фрагментах.
   Нормализация убирает регистр и пунктуацию, приравнивает ё к е; числа,
   повторы и термины автоматически не исправляет. Общий WER взвешен по словам.
5. Отдельно вручную отметить ошибки терминов, отрицаний, чисел, выдуманные фразы,
   пропуски смысла и точность таймкодов. Для кандидатов измерить время правки
   транскрипта до одинакового уровня готовности. Один WER не выбирает победителя.
6. Подтвердить результат на часовой выборке и непрерывной длинной записи.
   Если менять VAD или настройки после первой проверки, оставить отдельные
   фрагменты для финального теста и заново измерить итоговую конфигурацию.

Правило решения: сначала смысловая и терминологическая точность, затем время
человеческой правки, затем скорость/ресурсы. При близком качестве предпочтителен
более быстрый вариант. Существующая выборка мала и может содержать повторяющиеся
уроки; она даёт предварительный выбор, который нужно проверить на свежем корпусе.
Согласие моделей — сигнал для сортировки проверки, не доказательство точности.

NotebookLM остаётся отдельным кандидатом до сопоставимого теста по тому же аудио
и доступности полного транскрипта. Его конспект нельзя сравнивать по WER с дословной
расшифровкой. Доступ к нему сейчас не восстановлен.

## Что готово и что блокирует результат

Измерения скорости завершены: [отчёт](wiki-pipeline-progress-2026-09-28.md).
`scripts/wiki_asr_score.py` считает замены, удаления, вставки и WER только по
эталону, отмеченному как прослушанный. Проверяет хеш реального аудио, одинаковые
ID и наличие результатов всех трёх моделей. Частичное покрытие явно показывается.

```sh
python3 scripts/wiki_asr_score.py --root data/wiki-pipeline/2026-09-28/asr-comparison
```

Результат — приватный `quality.json`. На текущем незаполненном эталоне:
`awaiting_listened_reference`, 0 из 5 фрагментов, WER отсутствует.
Прямое прослушивание локального аудио недоступно инструментам агента в этой
задаче. Нужен слушатель для эталона; дополнительные ASR-прогоны его не заменяют.
Финальное решение по движку и массовый запуск до этого не выполнены.


## Актуальная схема: машинный эталон без ручной расшифровки

Владелец поручил заменить ручную работу независимыми сильными аудиомоделями.
Предлагаемая пара по официальной документации, проверенной 28 сентября 2026:

- [GPT-Transcribe](https://developers.openai.com/api/docs/models/gpt-transcribe),
  аудиофайлы, языковые и терминологические подсказки. Тариф $0,0045/мин,
  то есть $0,27 за 60 минут одного прохода.
- [Gemini 3.5 Transcribe](https://ai.google.dev/gemini-api/docs/transcribe),
  режим verbatim, без smart-редактуры, с временными метками слов.
- Для спорных отрывков — отдельный запрос с самим аудио к модели
  [Gemini с аудиовходом](https://ai.google.dev/gemini-api/docs/audio).
  В текущих примерах документации указан gemini-3.8-flash. Это повторная
  проверка, а не третий статистически независимый источник истины.

Это кандидаты для практического теста, не доказательство мирового лидерства
или превосходства на русской терминологии школы. Доступность в аккаунтах ещё
не проверена. Оценка Google и суммарный бюджет требуют проверки выбранного тарифа.

Алгоритм:

1. Использовать одинаковые аудиофрагменты и хеши. Сначала 7,5 минуты, затем час.
   Два облачных прохода получают только аудио и одинаковые инструкции о дословности,
   без результатов локальных моделей и без текстов друг друга. Первый проход без
   словарных подсказок; отдельный эксперимент со словарём фиксируется отдельно.
2. Сохранить оба исходных ответа, версии, настройки, стоимость и тайминги.
   Сопоставить тексты по словам, учесть запись чисел отдельно от лексических ошибок.
3. По расхождениям выделить аудио с контекстом. Повторная аудиопроверка сначала
   делает свою расшифровку, затем получает анонимизированные варианты; может
   оставить результат uncertain. Повторные запросы ограничены двумя попытками.
4. Сохранить машинный reference с происхождением каждого интервала: agreed,
   adjudicated или uncertain. Не выставлять verified_by_listener=true.
   Согласие не означает доказанную правильность: возможны общие ошибки.
5. Для всех локальных моделей измерять расстояние WER отдельно до каждого
   облачного текста на полной выборке и до составного машинного эталона.
   Для уверенной части показывать одинаковую маску интервалов и долю покрытия;
   нерешённые места учитывать отдельно, не скрывать их исключением из знаменателя.
6. Отдельно автоматический аудитор проверяет термины, отрицания, числа,
   выдуманные фразы и пропуски; это оценки модели, не человеческая валидация.
   Добавить отрицательные контроли: тишина и шум. Проверить часть совпавших мест,
   чтобы разбирать не только очевидные расхождения.
7. Выбрать локальную модель, если её преимущество устойчиво к обоим облачным
   reference и на разных записях. Если ранжирование меняется, зафиксировать
   неопределённость и расширить выборку, а не объявлять победителя по одному судье.

Результат называется «сравнение с машинным эталоном», а не истинной точностью.
Время человеческой правки без человека не измеряем; вместо него — число и типы
автоматически обнаруженных проблем. Неуверенные утверждения не превращать в
факты вики: оставить пометки или исключить из итоговой статьи.

Плановая рабочая схема: локальная транскрибация всего корпуса → облачная проверка
сомнительных фрагментов и случайной контрольной выборки → редактура → проверка
утверждений по транскрипту → кандидаты в вики/словарь. Финальный ASR выбирается
по результатам теста. Облачные модели получают только выбранное аудио, не весь
Telegram-архив.

Статус: метод выбран для реализации; облачные вызовы ещё не выполнены.
Существующий wiki_asr_score.py намеренно остаётся оценщиком ручного эталона.
Для машинного режима нужны отдельные provenance, masks и отчёт; подделывать
флаг прослушивания ради обхода проверки нельзя. Нужен настроенный API-доступ
к обоим провайдерам; наличие ключей не проверялось в этой исследовательской задаче.

## Текущее направление: без пополнения облачных API

Владелец отказался пополнять OpenAI ради разового теста. Облачный вариант выше
остаётся альтернативой; на текущем этапе платные запросы не запускаем.

Предлагаемое сравнение состоит из двух частей:

1. Внешний готовый эталон: русский test split google/fleurs, аудио и готовые
   транскрипции. Фиксируем ревизию и список ID до запуска, первый пилот — 100
   записей, одинаковых для всех движков. Считаем WER и CER, ошибки по записям,
   скорость и память. Не используем test для подбора промптов или настроек.
   Это чтение текстов, а не лекции школы; результат не переносится напрямую
   на специальные термины, шум и спонтанную речь. Возможное пересечение с
   обучающими данными моделей остаётся ограничением публичного benchmark.
2. На наших 7,5 минуты, затем часе аудио добавить Qwen3-ASR-1.7B как независимую
   по семейству контрольную модель к Whisper и Parakeet. Модель поддерживает
   русский язык; есть реализация mlx-audio для Apple Silicon. Предпочтителен
   BF16 при наличии совместимых весов и успешном пилоте на M4 Pro 48 GiB.
   Это специализированная ASR-модель, отличная от ранее обсуждавшегося
   текстового Qwen3.6 в Ollama.

На материалах школы измеряем расхождения, а не истинный WER. Whisper large и
Turbo не считать двумя независимыми голосами. Не оценивать Qwen относительно
консенсуса, в который он сам входит; показывать попарную матрицу и результаты
внешнего теста отдельно. Сомнительные отрывки повторно обрабатывать с контекстом,
сохранять неопределённость. Совпавшая ошибка нескольких моделей всё ещё возможна.

Если на внешнем тесте и наших записях появляется устойчивый практический лидер,
он становится основным кандидатом для очереди; второй движок проверяет
сомнительные места и случайную выборку. Преимущество на терминах школы без
независимого эталона остаётся гипотезой. Ручная расшифровка владельцем не нужна.

Официальные источники проверены 28 сентября 2026:
- https://huggingface.co/datasets/google/fleurs
- https://huggingface.co/Qwen/Qwen3-ASR-1.7B
- https://github.com/Blaizzy/mlx-audio/blob/main/mlx_audio/stt/models/qwen3_asr/README.md

Статус: источники и совместимый путь запуска найдены; FLEURS и Qwen ещё не
скачаны и не измерены. Расходов на API в этом варианте нет, остаются локальные
вычисления, скачивание весов и место на диске. Существующие настройки Ollama
и работающие проекты не меняются.


## Запуск бесплатного теста

После подтверждения владельца подготовлены отдельное qwen-venv и инструменты
wiki_qwen_asr.py / wiki_fleurs_benchmark.py. Используется mlx-audio 0.5.6 и
MLX 0.32.2; загрузка модели Qwen3-ASR-1.7B BF16. Сервер rows FLEURS вернул
HTTP 500; выбран прямой официальный Parquet русского test split с фиксацией
commit SHA. Первые 100 строк выбираются до inference. Результаты и аудио
сохраняются только в игнорируемом data/wiki-pipeline/2026-09-28/.


Бесплатный сравнительный пилот завершён: [замеры и рекомендация](wiki-local-asr-benchmark.md).
100 записей FLEURS обработаны всеми четырьмя моделями; Qwen также проверен
на 7,5 минуты материалов школы и цифровой тишине. Для следующей партии
рекомендованы Turbo как основной ASR и Parakeet как независимая проверка;
Qwen — дополнительный проход спорных фрагментов, не эталон. Массового запуска нет.


По следующему поручению владельца завершён [батч полных записей](wiki-real-batch-2026-09-28.md):
5 файлов / 4 ч 10 мин, Turbo+Parakeet, VAD и дополнительные Qwen-пробы.
Получены черновики, обнаружены вероятный дубль, служебные токены Parakeet и
повторы Qwen; 53 фрагмента остаются в очереди проверки. Автопубликации нет.
