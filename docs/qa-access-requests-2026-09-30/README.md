# Заявки на доступ — реализация и QA, 30 сентября 2026

Статус: локальная реализация. В этой задаче Railway не обновлялся, флаг заявок
не включался, новый TestFlight не загружался. Это не акт полной визуальной приёмки.

## Принятое поведение

Все новые заявители получают доступ только после решения организатора. Имя и
фамилия обязательны, Telegram необязателен и не удостоверяет личность. Админка
показывает заявку и возможные совпадения, но не объединяет людей автоматически.
Одобрение открывает доступ телефону без пересылки кодов. Старые приглашения
сохранены как запасной путь. Выход/отзыв закрывают прежнюю сессию; новая заявка
требует нового решения. Данные и закладки между телефонами не синхронизируются.

Уведомления организатору: существующий feedback-бот, нейтральный текст и ссылка
на защищённую карточку. Имена/контакты и секреты в Telegram не отправляются.
Очередь сохраняется в SQLite, с ограниченными повторами; отказ Telegram не теряет
заявку. Таймаут после доставки может дать повторное уведомление. Push участнику нет.

## Что реализовано

- `request-client.ts`: черновик и два независимых случайных секрета в SecureStore;
  обязательная запись до HTTP; одинаковые повторы после потери ответа/рестарта.
- Форма, ожидание, успех, отказ, новая заявка; проверки при открытии приложения и
  пока экран ожидания видим. Компактный ввод персонального приглашения.
- Закрытая вики показывает состояние заявки; возвраты к вики, настройкам и
  конкретному занятию. Нативный Back модального экрана учитывает вложенный ввод.
- Админка: список, фильтр, поиск имени/Telegram, карточка, одобрение/отказ,
  подтверждение отказа, hash-навигация после входа, запрет решения по устаревшему
  списку, очистка персональных данных страницы при выходе.
- Сервер: секреты только в виде хешей; изоляция admin cookie/CSRF от bearer
  участника, идемпотентные решения и получение сессии, ограничения спама.
- Последовательная запись сессии в Keychain: старый claim/logout/401 не стирает
  новый вход. Проверка при foreground не теряет одноразовое приглашение,
  которое активируется одновременно.

  ключом, установлен в существующий Android API36 эмулятор. Не для распространения.

iPhone + Chrome, настоящие локальные API/SQLite, вымышленные заявители:

1. Вики → заявка QA Applicant без Telegram → одна ожидающая запись в админке.
2. Одобрение в браузере → автоматическое «Доступ открыт» на iPhone → тестовый
   каталог вики, без ввода кода. После rebuild/restart доступ сохранился.
3. Выход на телефоне → повторная заявка. Отказ через диалог админки →
   «Заявка отклонена» на iPhone → новая форма с сохранёнными именем/фамилией.
4. Форма → персональное приглашение → верхний Back → форма с тем же черновиком.
   Прямой вход из gate в приглашение → Back возвращает к gate, а не к форме.
5. Таб «Расписание» из заявки → следующая неделя → Нейгун 7 октября →
   запрос доступа к Zoom → ожидание → возврат в то же занятие → повторный вход.
   После одобрения кнопка возвращает к Нейгун 7 октября 10:00–11:00.
   QA Zoom-каталог пустой: реальную Zoom-встречу эта проверка не открывала.
6. Выход организатора очищает страницу; повторный вход по hash открывает ту же
   карточку. Повторная заявка помечается как возможное совпадение.
7. Chrome viewport 390: фактические innerWidth/scrollWidth = 390/390, карточки и
   диалог отказа доступны. Проверен также desktop 1200 px.

Android API36, ADB с явного разрешения владельца:

- Пустая форма показывает ошибки имени/фамилии, без отправки HTTP.
- Форма → приглашение → аппаратный Back → форма: AndroidQA сохранено.
- Back из формы возвращает в вики; прямой ввод приглашения из вики возвращает в gate.
- Черновик сохранился после force-stop/relaunch и обновления QA APK.
- Расписание → следующая неделя → Нейгун 7 октября → доступ к Zoom →
  аппаратный Back возвращает к тому же занятию.
- Android использовал production URL; валидные заявки не отправлялись.

Дополнительный iOS E2E: API остановлен → понятная ошибка без native stack trace →
API запущен → «Отправить ещё раз» → ожидание. В SQLite ровно одна новая строка
(итого четыре синтетические заявки, одна pending), прежние данные сохранены.
Перезапуск QA API завершил admin-сессию: форма входа не содержит данных заявителя,
повторный вход восстановил исходную карточку по hash.

## Изоляция QA и артефакты

iOS собран с временным override `https://localhost:8879`. В симулятор добавлен
локальный двухдневный CA; macOS trust store не менялся. API работал с отдельными
SQLite и одним вымышленным wiki-материалом. Бот в QA отключён. После проверки локальные API/адаптер и Android-эмулятор остановлены, временный viewport Chrome сброшен.

Chrome использовал localhost HTTP адаптер: он проверял сертификат upstream HTTPS,
переводил Origin и имя/Secure атрибут cookie только для синтетической QA.
Поэтому браузерная проверка не доказывает production TLS/Secure cookie; серверные
тесты отдельно проверяют HTTPS origin/CSRF/cookie. В production этот адаптер не входит.

Исходники: HEAD `e505400` + незакоммиченный рабочий каталог с параллельными задачами;
точные SHA256 затронутых исходников — `source-sha256.txt`. Отдельного release tag нет.
QA Android APK: `data/android-qa/access-requests-2026-09-30-debug-signed.apk` (ignored).
SHA256 `cfe46d14c3356dacba25d2f372690c3098fca6980eac241aa5361cf15fbf7233` — финальная
локальная QA-сборка этого этапа.
