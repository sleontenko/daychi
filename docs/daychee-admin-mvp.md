## Что нужно в первой версии

Одна защищённая веб-страница: приглашения и компактный блок состояния сервиса.
Один администратор. Без отдельного мобильного приложения, CRM, платежей,
управления ролями, массовых рассылок и собственного редактора расписания.

### Приглашения и доступ

Создать → необязательная короткая метка (например, «Участник А, второй телефон»)
→ скопировать готовый текст с HTTPS-ссылкой и кодом → самостоятельно отправить.
Приложение не подтверждает доставку сообщения и не пишет человеку автоматически.

Список с поиском по метке и фильтрами «Ожидают / Доступ открыт / Завершённые».
В строке метка, статус, дата; действия по необходимости. Каждая запись относится
к одному приглашению/телефону, а не к подтверждённой личности человека.

| Условие | Статус | Действие |
|---|---|---|
| Не использовано, срок не истёк | Ожидает | Отменить приглашение |
| Не использовано, прошло 7 дней | Истекло | Выдать новое |
| Использовано, есть действующая сессия | Доступ открыт | Отозвать доступ |
| Использовано, сессии больше нет | Вышел на телефоне | Выдать новое |
| Отозвано организатором | Отозван | Выдать новое |

Истечение 7 дней закрывает только активацию, не уже открытый доступ.
Отзыв требует подтверждения: последующие защищённые запросы телефона запрещены.
Уже прочитанное/скопированное у человека удалить невозможно. Выдача нового
приглашения не должна молча отзывать другой телефон или менять срок старого.

Сервер хранит только хеш кода; после создания секрет показан однократно.
Повторное копирование из истории не обещаем. Пока окно результата открыто,
копирование можно повторить. После закрытия/потери результата — проверить список,
отменить неиспользованное приглашение и осознанно создать новое. Ошибка копирования
оставляет выделяемый текст; ошибка сети сохраняет черновик.

Двойное нажатие и повтор HTTP-запроса не создают второе приглашение: нужен
идентификатор операции с уникальностью в БД. При потерянном ответе проверять
результат по операции, не сохранять исходный секрет ради повторной выдачи.

### Минимальная аналитика

- Выдано приглашений и активировано за выбранный период (по умолчанию 30 дней).
- Открытых доступов сейчас: число телефонов с действующей сессией.
- Отдельно ожидающие и истёкшие приглашения, чтобы видеть проблемы входа.

Это показатели выдачи доступа, не DAU/MAU и не точное число участников.
Нет истории чтения, поисковых запросов, переходов в Zoom, выбора занятий,
рекламных идентификаторов, записи экранов и внешнего аналитического SDK.
Реальную вовлечённость на этом этапе выясняем через обратную связь.

### Минимальное обслуживание

- Railway: состояние процесса, рестарты, CPU/RAM, расходы; логи без кодов,
  ссылок приглашения, Authorization, Zoom и текста материалов.
- Проверка публичного API и свежести расписания отдельно: HTTP 200 у `/health`
  не означает, что каталог и источник расписания доступны.
- Ежедневная согласованная резервная копия SQLite через backup API, а также
  идентификаторов вики и закрытой конфигурации. План хранения 7 ежедневных копий;
  успешность определяется фактом завершения, отсутствие данных — «неизвестно».
- До запуска проверить восстановление в отдельный каталог и сохранение отзывов,
  сессий и стабильных ID. Копия на том же диске не защищает от потери диска:
  требуется отдельное место хранения, согласованное перед переносом секретов.
- Один канал технических оповещений об отказе и восстановлении; получатель и
  внешняя проверка ещё не настроены. Автоматические сообщения не отправлялись.
- Обратная связь пользователей остаётся через существующий Telegram-путь.

Не добавлять отдельные Grafana/Prometheus, очередь событий или платную платформу
аналитики для этой версии. Сбор ошибок приложения и статистика использования —
следующий этап только при реальной необходимости и с обновлением privacy-описания.

## Технические границы реализации

Один Python-сервис и постоянный volume; текущая SQLite достаточна по структуре
задачи, нагрузку проверить до выпуска. Добавить метку, даты создания/активации/
отзыва, журнал административных операций без секретов. Старые даты активации
не выдумывать: неизвестные значения сохранять NULL, исключать из периодных метрик.
Миграция обратно совместима со старыми токенами и сессиями, проверяется на копии БД.

Авторизация админки отделена от приглашений: обычный пользователь никогда не
получает права выдачи/отзыва. Способ входа владельца ещё предстоит выбрать при
реализации; минимальный вариант — один администратор, серверная сессия и защищённая
HttpOnly/Secure/SameSite cookie, CSRF-защита, ограничение попыток. Секрет не в URL,
JS-бандле или localStorage. Доступ к списку и метрикам проверяется на сервере.
При отсутствии конфигурации администратора endpoint закрыт по умолчанию.

Для Railway отдельно проверить доверенные proxy-заголовки и лимит попыток входа:
Fly-Client-IP из подготовленного варианта Fly неприменим. Не доверять произвольному
X-Forwarded-For, не считать всех посетителей одним IP внутреннего прокси.

без секретов и счётчики выдачи/активации. Публичных административных HTTP-маршрутов

включая параллельную миграцию старой схемы, сохранение старой сессии, отзыв,
различение истечения приглашения и срока доступа, отсутствие хешей в списке.
Production БД не изменялась. Идемпотентное создание, админ-авторизация, журнал,
веб-интерфейс, мониторинг и backup остаются следующим этапом.
CLI дополнен `list`, `summary` (30 дней) и `issue --label`; list/summary проверены
на пустой отдельной временной БД. Выдача настоящих приглашений не выполнялась.

Дизайн-кандидат → просмотр владельцем → реализация и сравнение на телефоне/desktop.
Проверить все состояния списка, длинные метки, клавиатуру, ошибки и возвраты.
