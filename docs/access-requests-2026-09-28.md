## Подтверждённая цель

Участник сам представляется и подаёт заявку. Организатор видит её в админке,
одобряет без создания и пересылки кодов. Приложение получает доступ после
одобрения. Организатору нужны уведомления о новых заявках, предложен Telegram.
Имя и фамилия обязательны; Telegram — необязательный контакт, не удостоверение
личности. Существующие приглашения и активные сессии должны продолжить работать.

Владелец подтвердил: всем новым заявителям доступ после одобрения, общая ссылка
с автоматическим доступом откладывается. Для уведомлений использовать
существующего бота. Существующие активные доступы не отзывать.

## Предлагаемая минимальная реализация

- Новые заявки хранятся на сервере независимо от доставки уведомления.
- Телефон сохраняет случайный секрет заявки в SecureStore до первой отправки;
  сервер хранит только его хеш. Публичного поиска по имени/Telegram нет.
- Повтор отправки с тем же идентификатором не создаёт вторую заявку; изменение
  содержимого под тем же идентификатором отклоняется. Потерянный ответ безопасно
  перепроверяется. До одобрения секрет заявки не даёт доступ к вики/Zoom.
- Решение организатора требует существующей отдельной admin-сессии и CSRF.
  Одобрение атомарно создаёт право доступа для заявителя; повтор не создаёт
  дополнительные права. Получение сессии телефоном должно допускать повтор
  после потери ответа без хранения открытых токенов на сервере.
- Статус проверяется при возвращении в приложение и на видимом экране ожидания.
  Не обещать push участнику или открытие доступа без сети.
- Для Telegram предлагается нейтральное уведомление «Новая заявка» с переходом
  в защищённую админку; имя и контакт остаются в админке. Ссылка не содержит
  секретов и не одобряет заявку. Вход возвращает к нужной заявке.
- Доставка через сохраняемую очередь с ограниченными повторами; недоступность
  Telegram не отменяет заявку. Возможность повторной доставки при сетевом
  таймауте должна быть честно отражена, не обещать exactly-once у sendMessage.
- После переустановки без сохранённого секрета — новая заявка; не объединять
  пользователей автоматически по самостоятельно введённому имени/Telegram.

## Обязательные проверки

Заявка → ожидание → одобрение → доступ; отказ; отзыв; перезапуск приложения;
потерянный ответ отправки/одобрения/получения доступа; конкурирующие повторы;
неверный секрет; запрет чтения чужих заявок и действий участника в admin API;
CSRF/origin; постоянные ограничения спама; отсутствие секретов в URL/логах;
отказ Telegram и повтор доставки; старые приглашения и сессии без регрессий.

Парная визуальная QA каждого нового состояния и возвраты из вики/Zoom,
клавиатура/safe areas, Android Back, сохранение черновика и исходного экрана.
До выполнения не называть сценарий готовым и не выпускать новую сборку.

## Локальная серверная реализация

Добавлены отдельные модули access_requests, access_request_api и
access_request_notifications. Маршруты POST/GET `/api/access/request`, POST
`/api/access/request/claim`, защищённые GET `/api/admin/requests` и POST
`/api/admin/requests/{id}/approve|reject`. Используются прежние admin session/CSRF.
Очередь Telegram переживает рестарт, использует существующие серверные настройки
бота обратной связи, не читает updates и не меняет webhook. Уведомление не содержит
имени, контакта или секрета; ссылка `/admin#request=ID` требует admin-входа.
Доставку новой заявки в настоящий Telegram ещё не проверяли.

40 локальных Python-тестов прошли: новый поток заявок/уведомлений/API и регрессии
admin, access, inventory, feedback, proxy. В том числе полный HTTP-путь заявки,
одобрения и claim на изолированной базе, конкурентные повторы, выход/отзыв,
запрет участникам admin API, CSRF, отказ Telegram, постоянные лимиты, запрет
перехвата старой сессии и отсутствие секретов в возвращаемом списке.
Это не UI E2E и не production-проверка. Клиент приложения и интерфейс админки
пока не подключены; переход из Telegram заработает после интеграции UI.
Функция отключена по умолчанию: `DAYCHEE_ACCESS_REQUESTS_ENABLED=1` включает
маршруты и worker вместе. Не включать до подключения/приёмки обоих интерфейсов.
Это защищает от случайного запуска незавершённого сценария при параллельном
выпуске других изменений из общей рабочей папки.

на скриншотах браузера. Это демо, реальных заявок и уведомлений не создавали.
