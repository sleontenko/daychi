# Дейчи: публичный вход без Tailscale

24 сентября 2026. Пользователь подтвердил, что на его iPhone прежний API
доступен только при включённом Tailscale. Это блокер реального использования,
несмотря на успешные проверки публичных IP с Mac и вход на эмуляторах.

Hobby подключён в интерфейсе Railway 25 сентября с явного разрешения владельца.
28 сентября подтверждены и сохранены compute hard limit $10 и предупреждение $5.
Сервис и приватные данные пока не перенесены. План минимальной админки и текущий
статус: [управление Дейчи](daychee-admin-mvp.md).

1. Организатор выдаёт обычную HTTPS-ссылку `/invite#CODE` и код из 12 символов.
2. Ссылка открывает страницу с кнопкой «Открыть Дейчи» и копированием кода.
3. Если открытие приложения не сработало, пользователь открывает Вики и вставляет
   код либо полную ссылку. Адрес из вставленной ссылки не выбирает API-сервер.
4. Активация даёт доступ на этом телефоне. Повторное использование невозможно.

Срок активации 7 дней, один телефон, доступ до отзыва или выхода сохранены.
Старые длинные приглашения и существующие сессии поддерживаются при переносе БД.
Страница ничего не активирует автоматически: предпросмотр мессенджера не расходует
приглашение. Короткий код имеет почти 60 случайных бит; на сервере хранится только
SHA-256. Ограничение активаций общее для старого и нового endpoint: 10 попыток
за 10 минут на IP в одном worker. В Fly учитывается перезаписываемый edge-заголовок
Fly-Client-IP, а не произвольный X-Forwarded-For.

Не объявлять это Apple Universal Links / Android App Links: на данном этапе HTTPS
ведёт на страницу, а её кнопка открывает приложение через зарегистрированную схему.
Код остаётся независимым запасным способом. Публичная ссылка установки пока не
настроена: бета распространяется отдельным приглашением TestFlight.

## Подготовленная инфраструктура

`deploy/daychee/`: минимальный Dockerfile, фиксированные прямые зависимости,
Fly config (fra, одна 512 MB shared CPU машина, постоянный volume, snapshots 7 дней).
Build context ограничен allowlist: ни индекс вики, ни Zoom, ни базы/credentials
не отправляются builder и не попадают в образ. Процесс после подготовки каталога
volume работает под UID/GID 10001; umask 077, access logs выключены.
В образе только маршруты нового API и публичное расписание; старый корпус API
не копируется и не подключается. `/health` проверяет работу процесса, а не наличие
всего каталога: после переноса нужна отдельная авторизованная проверка данных.

Закрытые данные переносятся отдельно на volume после согласования владельцем:
индекс, SQLite идентификаторов, SQLite приглашений/сессий и Zoom JSON. Перед
переносом SQLite нужны согласованные backup-копии, а не копирование открытого файла.
Нельзя независимо выдавать и отзывать доступ в старой и новой базе после cutover.
Старый адрес требуется отключить или перевести на новый единственный источник
авторизации после проверки нового сервиса. Бэкап не восстанавливать поверх новых
выданных доступов без отдельного плана согласования состояний.

Данные APNs не переносятся: в прежней production БД devices.sqlite3 обнаружено
0 зарегистрированных устройств (read-only проверка 24 сентября). Приложение
использует локальные уведомления. Поведение старого невалидного device-ключа
не должно давать фиктивного подтверждения отключения серверных уведомлений.

## Осталось до готовности

Согласовать лимит расходов, развернуть и проверить Railway, перенести
данные без потери ID/сессий, переключить обе public env-переменные приложения,
проверить вход/отзыв на новой нативной сборке. Затем подготовить новый TestFlight
и получить разрешение выпуска. Приёмка — вход владельца с **выключенным Tailscale**,
по Wi-Fi и мобильному интернету. До этого не объявлять проблему решённой.

CLI Fly подключён к аккаунту владельца; организация MyPraxis подтверждена.

закрытых данных. На момент этой записи ответ ещё не получен, ресурсов Дейчи

## Уточнение владельца: использовать существующую машину

Владелец предложил использовать уже работающую машину вместо нового сервиса
с отдельной оплачиваемой VM. Предыдущий запрос на создание новой VM/volume
**не подтверждён**; отдельную машину не создавать по прежнему плану.

Read-only проверка Fly: у `masik-web` worker 2 GB работает, web 2 GB при проверке
находился в suspend; есть также остановленная web-машина 2 GB. У web/worker нет
постоянных volumes. `masik-web-db` — работающая PostgreSQL-машина 512 MB с одним
volume. Это конфигурация, а не замер свободных ресурсов или нагрузки.

Размещение полноценного backend Дейчи на той же web-VM технически возможно,
но требует общей сборки/маршрутизации с Масиком и отдельного постоянного хранилища
данных Дейчи (например, отдельной БД и роли в существующем PostgreSQL после
проверки ёмкости). Нельзя просто положить рабочие SQLite/JSON на ephemeral-диск
web-VM или добавить process group: новый process group создаёт отдельную VM.
Нельзя запускать backend на PostgreSQL-машине или тяжёлом worker только потому,
что они сейчас находятся в started.

Подготовленный `deploy/daychee/fly.toml` остаётся вариантом **отдельной машины**,
а не готовым конфигом совместного размещения; его не применять к `masik-web`.
Совместный вариант свяжет обновления/перезапуски двух продуктов и увеличит нагрузку
и, возможно, время работы web-VM. Бесплатность или достаточность ресурсов пока
не подтверждены. Изменений в production Масика и его данных не выполнено.
